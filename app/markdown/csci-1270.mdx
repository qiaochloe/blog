## Database Management System

The database symbol is a cylinder because databases were originally stored on a hard disk of stacked plates.

**Question**: Why use a database management system (DBMS) instead of a filesystem?

1. Data consistency (schema)
2. Crash recovery
3. Efficient data retrieval 
4. Concurrent access to data
5. Physical data independence (ability to change how data is stored without changing application code)

A DBMS allows users to store, query, and update databases in accordance to some data model. Examples of data models include:
1. Relational
2. Key-value
3. Graph
4. Document 
5. Vector

DBMS design principles:
1. More specialized databases, driven by application semantics
2. Few primitives (relational operators) which can be composed
3. Data independence; applications should not need to understand how data is stored
4. Declarative programming

### Relational Algebra

Early database applications tightly coupled logical and physical layers, which made it difficult to make any changes to the program. To deal with the maintenance overhead, Ted Codd wrote [A relational model of data for large shared data banks](https://dl.acm.org/doi/10.1145/362384.362685), which later became the basis of the relational data model.

The key ideas are:
- Data should be stored in simple data structures (relations)
- The DBMS should be responsible for the physical storage of the data
- Data should be accessed through high-level, declarative language, so that the DBMS can optimize it

Terminology:
- A relation is an unordered set of tuples
- A tuple is a set of attribute values
- A primary key uniquely identifies a single tuple in a relation
- A foreign key specifies that an attribute from one relation maps to a tuple in another relation

Relational models can define constraints, such as:
- Table schema is respected
- Primary keys are unique
- The foreign key exists in another table
- Global assertions

There are two different types of data management languages (DMLs):
1. Procedural: the query specifies how to find the desired result (e.g. relational algebra)
2. Declarative: the query only specifies what data is wanted (e.g. SQL)

Relational algebra is based on set algebra. That means that it represents relations as unordered lists with no duplicates. Each operator takes in one relation and outputs a new relation. 

| Symbol                           | Meaning                                                                        |
|----------------------------------|--------------------------------------------------------------------------------|
| $\sigma_{\text{pred}}(R)$        | Select all tuples which satisfy `pred`                                         |
| $\pi{\text{A1, A2, ..., An}}(R)$ | Generate a relation with only the specified attributes                        |
| $R \cup S$                       | Generate a relation that contains all tuples that appear in either relation    |
| $R \cap S$                       | Generate a relation that contains all tuples that appear in both relations     |
| $R - S$                          | Generate a relation that contains all tuples that appear in $R$ but not in $S$ |
| $R \times S$                     | Generate the Cartesian product of the two relations                            |
| $R \bowtie S$                    | Perform a natural join; only return tuples which have common attributes        |

### SQL

Unlike in relational algebra, SQL assumes that data is stored in a bag, not a set. This means that there can be duplicated rows. This is for efficiency reasons—if we do a union on two very large tables, it is expensive to deduplicate the output.

There are several classes of SQL operations:
1. Selection ($\sigma$)
2. Projection ($\pi$)
3. Aggregation
4. Join
5. Views

`GROUP BY` rules:
1. Non-aggregated values in `SELECT` output must appear in `GROUP BY` clause.
2. Each `GROUP BY` clause will cause the output to contain one tuple per group.

Types of `JOIN`:
- Cross join: Cartesian product
- Inner join: every pair that matches, dropping non-matching pairs
- Outer join: every pair that matches, keeping non-matching tuples

Within inner joins, there is:
- Natural join ($R \bowtie S$): match tuples where the shared attributes are equivalent
- Theta or equijoin ($R \bowtie_\theta S$): match tuples using some join predicate defined by $\theta$
- Semi join ($R \ltimes S$): same as theta join, except output relation only contains attributes from $R$
- Anti semijoin ($R \rhd S$): tuples of $R$ that do not match with any tuple of $S$ (not technically an inner join)

Within outer joins, there is:
- Left outer join ($R\, ⟕\, S$): match all combinations of tuples where the shared attributes are equivalent, plus all tuples in $R$ that have no match in $S$
- Right outer join ($R\, ⟖\, S$): the same as left outer join but reversed
- Full outer join ($R\, ⟗\, S$): union of left and right outer joins

For more details about SQL syntax, go to the [SQL](/sql) page.

A ==view== is a (virtual) table that is the result of a SQL query. Typically, user applications are built on top of views rather than the base tables. It is usually not possible to update a view.

Because views may be accessed frequently, it may be impractical to run the query every time. We may want to maintain a ==materialized view==, a cache of the view that is refreshed on updates or periodically.

### Schema Design

A good database schema ensures data integrity and has good performance. These goals are typically in conflict with each other. 

On one end of the extreme, we have only one spreadsheet with all the data. This has good performance because it is not necessary to perform any joins. But it is difficult to maintain data integrity with respect to updates, insertions, and deletions.

For example, consider the following spreadsheet:

| student_id | course_id | room | name  |
|------------|-----------|------|-------|
| 1          | 1         | 100  | Alice |
| 2          | 1         | 200  | Bob   |
| 2          | 2         | 200  | Bob   |

- If we want to update the room number for a particular course, we need to iterate through the entire database to update the fields
- We cannot insert a student that is not enrolled in a course
- If we delete all students enrolled in a course, we lose information about which course is assigned to which room

The alternative is to decompose the schema into multiple relations, or ==normalizing== the data. This reduces redundancy, which is good for data integrity. However, we will typically need more joins, leading to a decrease in performance.

There are multiple levels of normalization:

| Name                     | Description                                                                                                    |
|--------------------------|----------------------------------------------------------------------------------------------------------------|
| First Normal Form (1NF)  | Each cell should contain only a single value and not a list of values                                         |
| Second Normal Form (2NF) | A table should not contain any partial dependencies where a column depends on part of a composite primary key |
| Third Normal Form (3NF)  | A table should not contain any transitive dependencies where a column depends on another column                |

### Layers of a DBMS

1. The **storage manager** handles reading and writing raw pages to and from the physical disk
2. The **buffer pool manager** manages an in-memory cache of pages
3. The **access methods** determines how data is organized and accessed on disk
4. The **operator execution** describes how relational operators consume and produce tuples
5. The **query planner** parses, optimizes, and compiles a query into a plan of operators to execute

## Storage Manager

### Files and Pages

The DBMS stores the database as **files** on the disk.[^file] Files are organized as a collection of **pages** (or blocks).[^page] The ==storage manager== is responsible for reading and writing fixed-sized pages to and from the disk. 

[^file]: Typically in a proprietary binary format

[^page]: There are actually three different notions of pages in a DBMS:
    1. Hardware page, the atomic unit of I/O to a disk (4 KB)
    2. OS page, the software abstraction of a hardware page (4 KB)
    3. Database page, set by the DBMS (4-16 KB)

    Large database pages are good for large sequential writes, but it is more complicated to ensure atomicity. Additionally, more data needs to be loaded into RAM for small reads and writes. 

![File layout](/csci-1270/file-layout.png)

DBMSs try to ensure that consecutive pages are stored on consecutive disk blocks. On magnetic hard disks, doing random access costs seek time and rotational latency. While this is less significant for SSDs, there may be I/O controller overheads.

### Page and Tuple Layout

Every database page contains a header with metadata[^page-metadata] about the page's contents as well, as the actual **tuples**.

[^page-metadata]: Page metadata includes page size, checksum, DBMS version, transaction visibility, and compression information.

One naive way to lay out tuples on a page is by directly placing them in a fixed array of slots. However, this requires that each tuple be a fixed size. It also makes deletions difficult.

The most common layout scheme for a page is called ==slotted pages==. The slotted page adds another layer of indirection called the slot array, which maps slots to the tuple offsets. The header keeps track of the number of used slots and the offset of the last slot used.

Some benefits of the slotted pages are:
- During deletion, the slot array can be easily modified to hide the deletion 
- Slots can be heterogeneous sizes
- Compaction of the actual data can be delayed

![Naive vs. slotted pages approach](/csci-1270/slotted-pages.png)

The DBMS also needs a way to keep track of individual tuples. The tuple's identifier (also called record ID) is typically the page ID and the slot number. 

Tuples may have a header to specify things like the ==null value bitmap==. Having a null value bitmap allows us to save space, since we don't need to store the null value.[^null-value-bitmap-example] 

[^null-value-bitmap-example]: For example, a tuple with the value `{101, 13, null}` would have the null value bitmap 001, allowing us to only allocate `101` and `13` on the disk.

### The Operating System

Traditional file I/O operations involve system calls to read from or write to a file. Memory mapping (`mmap`) allows a file to be accessed directly through virtual memory addresses.

![MMAP](/csci-1270/mmap.png)

Many DBMSs *avoid* using memory-mapped files because they require fine-grained control over I/O operations. In general, DBMSs know more about their workloads and can better optimize file fetches and flushes than the OS. Sometimes, the OS can even get in the way, like in the case of double-buffering.

However, most modern operating systems *do* use the file system API exposed by the operating system. Early DBMS systems used custom file systems on raw storage, but this had portability issues when switching to different hardware, and the performance benefit was minimal (5-10%).

## Buffer Pool Manager

The buffer pool manager sits directly on top of the storage manager. It manages an in-memory cache of pages so that the DBMS does not need to hit the disk on every access. The cache is called a **buffer pool** and each page is called a **frame**.

The buffer pool manager handles:
- Fetching a page (from the buffer pool if cached, else asking the storage manager to read it from disk)
- Pinning and unpinning pages
- Deciding which page to evict when the pool is fool
- Marking pages as dirty and flusing them back via the storage manager

The ==page table== keeps track of pages that are currently in memory, and it also keeps additional metadata about the dirty flag and the reference count. The page table is usually a fixed-sized map protected with latches to ensure thread-safe access.

The DBMS *cannot* evict pages from the buffer pool if the reference count is non-zero. The DBMS should probably also write back the page to disk before eviction if the page is dirty. But the database wants to carefully control *when* dirty pages are written back to disk. It wants to use the RAM as a **write-back cache** for disk, not as a write-through cache.

## Access Methods

Access methods sit on top of the buffer pool manager. To find, insert, or delete a record, an access method uses a record ID to locate it. It then asks the buffer pool manager for the page by page ID, and then uses the page's slotted layout to find the tuple at the given slot number.

### File Organization

Here are some data structures for file organization:
- Heap file organization
- Hashing file organization
- Sequential or sorted file organization (ISAM)
- Tree file organization

A ==heap file== is a collection of pages with tuples that are stored in random order. A ==page directory== tracks the physical location of pages for a database file, and also records metadata about available space.

A ==hashing file== organization groups tuples by a hash of some attribute, so the underlying data structure is a hash table. A hash table[^hash-table] is an array of values. For a given `key` and number of slots `n`, we can compute `hash(key) % n` to get an offset into the array. 

[^hash-table]: For more information about different hashing schemes, see [Hash Tables](/data-structures-and-algorithms#hash-tables)

For a database, we want a hash function that is fast and has a low collision rate. We do not want or need cryptographic properties, like one-way or random oracle. Examples of good database hash functions include CRC-64, MurmurHash, Google CityHash, Facebook XXHash, and GoogleFarmHash.

### Table Indexes

The file organizations above describe how the base table itself is stored. A **table index** is a separate, redundant data structure built on top of the base table for efficient access using some attribute.

It is the job of the DBMS to:
- Ensure that the table and index are synchronized
- Figure out the best index to use during query execution

### B+ Trees

The standard index implementation is the ==B+ tree==.[^b-tree] A B+ tree is a self-balancing tree that keeps data sorted and allows searches, sequential access, insertions, and deletions in O(log n). 

[^b-tree]: A B+ tree is often used interchangeably with a B-tree. In a regular B-tree, keys and values are stored in all the nodes in the tree. A B+ tree stores values only in leaf nodes, and inner nodes are only used for search. While B-trees are more space-efficient, B+ trees are better for sequential or concurrent access.  

It should maintain the following invariants:
- It is perfect balanced, and every leaf node is at the same depth in the tree
- Every node other than the root is at least half-full

Let $n$ be the number of keys on a node and let $m$ be the maximum number of children of a node. Then it must be the case that:

$$
\lceil m / 2 \rceil - 1 \leq n \leq m - 1
$$

Every B+ tree node holds an array of key-value pairs. The keys are always derived from the columns the index is built on.[^b-tree-keys] The values differ by node type:
- In an inner node, the value is just a pointer to a child node
- In a leaf node, the data is either the actual tuple (in a clustered primary index) or a pointer to the tuple (in a non-clustered secondary index)

[^b-tree-keys]: For example, if you have an index on `user_id`, every node's keys are `user_id` values, kept sorted.

![B+ trees](/csci-1270/b-tree.png)

A B+ tree node also contains sibling pointers for the sibling pages on the left and right.

To search for a value, start at the root node and use binary search to descend to the right leaf node.

To insert, find the correct leaf and insert the entry in sorted order.

If the leaf is now over capacity, then:
1. Create a new leaf node and transfer half of the values (including the median) over to it
2. Copy the median key up into the parent as a separator for the two nodes

If that insertion overflows the parent too, split it the same way, but push up (rather than copy up) the middle key. Repeat up the tree until a node doesn't overflow, or a new root is created.

To perform deletion, find the leaf node and remove the entry. If the leaf node is no longer at least half-full, try to redistribute by borrowing from adjacent siblings. If redistribution fails, merge the leaf node with a sibling. If a merge occurred, we must delete the entry from the parent of the leaf node.

## Operator Execution 

Just as we cannot assume that a table fits entirely in memory, a disk-oriented DBMS cannot assume that a query result fits in memory. We will use the buffer pool to implement algorithms that need to spill to disk. We are also going to prefer algorithms that decrease the total amount of I/O. 

A few common operators are scans, sorts, aggregations, and joins.

### Scans

To get a list of tuples, we can either perform a sequential table scan or an index scan.

To perform a ==table scan==, for each page in the table:
1. Retrieve it from the buffer pool
2. Iterate over each tuple and check whether to include it

The DBMS maintains an internal cursor that tracks the last page and slot it examined.

To perform an ==index scan==, the DBMS uses the index to find the tuples that the query needs. In a multi-index scan, the DBMS needs to choose the indices it uses,[^which-index] and it may have to perform set intersection. Set intersection can be done with bitmaps, hash tables, or Bloom filters.[^bloom]

[^which-index]: For example, consider the query below:

    ```
    SELECT * FROM students
    WHERE age < 30
    AND dept = 'cs'
    ```

    If there is an index on `age` and an index on `dept`, one way to run the query is to use the indices to fetch records where `age < 30` and records where `dept = 'cs'`, and then take their intersection.

    We could also instead only use the `age` index and manually filter the `dept` condition. Or vice-versa. Or use neither indices.

[^bloom]: [Bloom Filters by Example](https://llimllib.github.io/bloomfilter-tutorial)

### Sorting

We may want our tuples to be sorted in a particular way in order to implement `ORDER BY`, `DISTINCT`, `GROUP BY`, or merge joins.

If the data fits in memory, then we can use a standard in-place sorting algorithm. If the data does not fit in memory, then we need to do some kind of ==external sorting==. One algorithm for external sorting is the external merge sort:
1. Sort chunks of data that fit in memory into sorted chunks (runs)
2. Combine runs into longer runs

Suppose we have $N$ pages of data to sort, but only $B$ buffer pages to work with at any time.

1. In the first pass, we repeatedly load $B$ pages, sort them in memory, and write them back out as a sorted run of size $B$. After this pass, we have $\lceil N / B \rceil$  sorted runs, each of size $B$. 

2. In subsequent passes, we need to merge sorted runs together. To merge $k$ runs simultaneously, we need $k$ input buffers plus $1$ output buffer to write the merged result. Because we only have $B$ buffers total, we can merge at most $B - 1$ runs at a time. 

Each merge pass reduces the number of runs by a factor of $B - 1$, since every $B - 1$ run gets merged into $1$. Thus, the total number of passes is given by $1 + \lceil \log_{B - 1} \lceil N / B \rceil \rceil$.

At each pass, we read and write each page once, so the total number of operations is 
$$
2N \cdot \left(1 + \lceil \log_{B - 1} \lceil N / B \rceil \rceil\right)
$$

### Aggregations

We may also want to quickly find tuples with the same distinguishing attributes for grouping.

There are typically two implementations of aggregations: sorting and hashing. Sorting aggregates is useful to fulfill `ORDER BY` and `DISTINCT` conditions. But if we do not need the data to be ordered, then hashing is usually a better alternative. 

#### Hash Aggregates

To perform hashing, we create a temporary hash table as the DBMS scans the table. For each record, we check whether there is already an entry in the hash table. For `DISTINCT`, we discard duplicates. For `GROUP BY` we perform the aggregate computation. 

Some aggregations can be done incrementally as each tuple is seen. We store pairs of the form `(group_key, val)`. If we find a matching `group_key`, we just update the `val`. Otherwise, we insert a new `(group_key, val)` pair. Aggregations where we can just maintain a running value include `SUM`, `COUNT`, `AVG`, `MIN`, and `MAX`. 

#### External Hash Aggregates

Using hashing for aggregation only works if everything fits in memory. Otherwise, we need to use an ==external hash aggregate==. Here is the divide-and-conquer algorithm:
1. **Partition phase**: Hash each row into one of several buckets based on the grouping key. Write each bucket out to disk.
2. **Rehashing phase**: Read in each partition, build an in-memory hash table for each partition, and compute the aggregation.

Suppose we have $B$ buffers. We will use $B - 1$ buffers for the partitions and $1$ buffer for the input data. We will use a hash function $h_1$ to split tuples into these partitions on the disk, and we will we flush the partition onto disk when the buffer page fills up.

After we do this, for each partition on disk, we will read it into memory and build a second hash function $h_2$. Then we'll go through each bucket of this hash table to bring together matching tuples. This assumes that each partition fits in memory.

Assuming we have $N$ total pages, we will need $2N$ operations (1 read and write) to partition the initial data and $N$ operations to rehash it. This gives us a total of $3N$, plus whatever needs to be done to the aggregation results. 

### Joins

There are several categories of join algorithms, including nested loop join, hash join, and sort-merge join. 

Suppose we want to perform a binary equijoin on $R$ and $S$, where $R$ has $M$ pages with $m$ total tuples, and $S$ has $N$ pages with $n$ total tuples.

#### Simple Nested Loop Joins

In a simple nested join loop, we scan the outer table once ($M$) and scan the inner tables once for each tuple in the outer table ($mN$). This will cost us $M + mN$ operations. Thus, in general, we want the smaller table to be the outer table.

```
foreach tuple r in R:
    foreach tuple s in S:
        if r and s match: output
```

#### Block Nested Loop Joins

A block nested loop join improves on the simple algorithm by loading as many pages of $R$ into memory at once as the buffer allows, instead of just one page at a time.

Suppose we have $B$ buffers available. We split them as:
- $B - 2$ buffers for holding one block of $R$
- 1 buffer for the current page of $S$ being scanned
- 1 buffer for storing the output being written

First, we need $M$ operations to read all of $R$. Because we have $B - 2$ buffers, we will need to process $\lceil M / (B - 2) \rceil$ blocks of $R$. For each block, we do one full rescan of $S$, costing $N$. This will give us a total cost of 
$$
M + \left(\lceil M / (B - 2) \rceil \cdot N \right)
$$

If the outer relation completely fits in memory, then the cost is just $M + N$. 

```
foreach block br in R:
    foreach block bs in S:
        foreach tuple r in br:
            foreach tuple s in bs:
                if r and s match: output
```

#### Index Nested Loop Joins

The basic nested loop join is inefficient because we need to do a sequential search over the inner table to check a match. Instead of doing a sequential search, we can also do an index nested loop join to find inner table matches.

Assuming that the cost of each index probe is some $C$ per tuple, the total cost is 
$$
M + mC
$$

```
foreach tuple r in R:
    foreach tuple s in index("r = s"):
        if r and s match: output
```

#### Hash Joins

For a hash join, the general algorithm is:
1. **Build phase**: Scan the outer table and populate a hash table using the hash function $h_1$ on the join attributes
2. **Probe phase**: Scan the inner table, and use $h_1$ on each tuple to jump to the matching bucket in the hash table 

During the build phase, we can also construct a Bloom filter.[^bloom] In the probe phase, we can check the filter first to skip probes that are guaranteed not to match.

[^bloom]: A Bloom filter is a probabilistic data structure that determines set membership. False negatives never occurs, but false positives can occur. On `insert`, we use `k` hash functions to set bits in the filter to 1. On `lookup`, we check whether the bits are 1 for each hash function. 

#### External Hash Joins

If the hash table doesn't fit in memory, then we need to perform an external hash join. One algorithm is called a partitioned hash join, or a ==grace join==.

First, we partition both $R$ and $S$ into buckets using a hash function $h_1$. We then perform a regular hash join on each pair of matching buckets using another hash function $h_2$. 

If a bucket pair still doesn't fit in memory, recursively partition it with a new hash function ($h_3$) until the pieces are small enough, then build a hash table on one side and probe with the other.

The partitioning phase will take $2(M + N)$ operations, since we need to read and write every page of both relations. Once the data is partitioned, we go bucket pair by bucket pair, reading each page exactly once for a cost of $M + N$ operations. This gives us a total cost of:
$$
3(M + N)
$$

#### Sort-Merge Join

In a sort merge-join, we:
1. Sort both tables on the join keys using an external merge sort
2. Step through the two sorted tables with cursors and emit matching tuples

This has a cost of:
- Sort cost for $R$: $2M \left( 1 + \lceil \log_{B - 1} \lceil N / B \rceil \rceil \right)$
- Sort cost for $S$: $2N \left( 1 + \lceil \log_{B - 1} \lceil N / B \rceil \rceil \right)$
- Merge cost: $M + N$

Sort-merge join is useful when the input tables are already sorted, if the output must be sorted on the join key, or if the relation doesn't fit in main memory. 

#### Summary

| Algorithm               | I/O Cost    |
|-------------------------|-------------|
| Simple Nested Loop Join | $M + mN$    |
| Block Nested Loop Join  | $M + \left(\lceil M / (B - 2) \rceil \cdot N \right)$ |
| Index Nested Loop Join  | $M + mC$    |
| Sort-Merge Join         | $M + N + 2S$ |
| Hash Join               | $3(M + N)$  |

## Query Planning

A DBMS converts a query into a plan comprised of logical operators. Data flows from the leaves up toward the root, which is the result of the query. 

![Query planning](/csci-1270/query-planning.png)

A DBMS's ==processing model== defines how the system executes a query plan. There are three main models: (1) iterator model, (2) materialization model, and (3) vectorized or batch model. 

### Iterator Model

In the iterator model, each query plan operator implements three functions: `open()`, `next()`, and `close()`. 

The model pulls tuples one at a time through a chain of `next()` calls. Each operator produces a single tuple on demand and passes it immediately to its parent, which processes it before asking for the next one.

This model allows for tuple pipelining. However, some operators like hash joins, hash aggregates, and `ORDER BY` must block until their child emit all their tuples. These are called pipeline breakers. 

Because only one tuple exists in flight per operator at any moment, there is no need to materialize a whole intermediate result set between operators. Furthermore, it is easy to implement `LIMIT`. 

![Iterator model](/csci-1270/iterator-model.png)

### Materialization Model

In the materialization model, each operator fully computes its output and passes the complete result to the next operator. 

Compared to the iterator model, materialization is simpler and can be efficient when each operator processes data in batches, since it avoids function call overhead. 

It is less memory efficient for large intermediate results, since the full output of every stage must be stored before the next stage starts. We can push down hints (e.g. `LIMIT`) to avoid scanning too many tuples.

![Materialization model](/csci-1270/materialization-model.png)

### Vectorization Model

The vectorized execution model is a middle ground between the iterator model and the materialization model. Instead of passing one row at a time (iterator model) or the entire result set at once (materialization model), each operator processes a **batch** of rows at a time. Typical batch sizes are in the thousands of rows.

Each operator pulls a batch from its input, processes the whole batch, and passes that batch to the next operator. This repeats until all batches are consumed.

Processing in batches amortizes the per-call overhead of the iterator model, since a function call now handles many rows instead of one. It also enables SIMD optimizations and better cache locality, since a batch of column values fits in cache.

It avoids the memory issues in the materialization model, since only one batch is held in memory at a time instead of a full intermediate result.

![Vectorization model](/csci-1270/vectorization-model.png)

## Query Optimization

Query optimization turns a query into an executable plan in two phases.

1. The ==logical plan== is a tree of relational algebra operators. The DBMS uses **heuristic** rewrite rules to transform the tree into an equivalent tree. The goal is the increase the likelihood of finding the optimal plan in the cost-based optimization phase.

2. The ==physical plan==[^phys-plan] assigns algorithms and access methods to each logical operator. Using a **cost model**, the optimizer searches the space of possible physical plans for the cheapest plan.

[^phys-plan]: In Postgres, `EXPLAIN` prints the plan chosen for a given query, plus the estimated cost and result set size. `ANALYZE` runs the query and prints the actual values.

### Logical Plan Heuristics

Some examples of logical plan heuristics are:
- **Split conjunctive predicates**. Decompose  a compound `AND` predicate into separate, individual filters so that it is easier for the optimizer to move them around.
- **Predicate pushdown**. Move the predicate to the lowest applicable point in the plan.
- **Replace Cartesian products** with inner joins using join predicates.[^replace-cart]
- **Projection pushdown**. Eliminate redundant attributes.

[^replace-cart]: For example, a query like `SELECT * FROM R, S WHERE R.id = S.id` will naively translate to a Cartesian product followed by a filter. We can instead do an inner join between `R` and `S` on the condition that `R.id = S.id`.

### Enumerating Physical Plans

First, the DBMS needs to estimate different plans:
1. For each table, we need to pick the best access path
2. Then we need to enumerate all possible join orderings for the tables
3. For each ordering we need to enumerate possible join implementations

To choose the join ordering and implement, one common approach is to use a ==left-deep join tree==, where every join's right input is a base table rather than an intermediate result:
1. Pick two tables to join
2. Pick a third one to join with the results as the right relation
3. Repeat until all tables are joined

Restricting the right input to a base table has two advantages
1. Enumerating orderings becomes a permutation problem (n! for n tables) instead of also enumerating tree shapes
2. Dynamic programming optimizers can cache and reuse overlapping subproblems
3. It also enables pipelining, since the base table on the right can be streamed without materializing intermediate results

A bushy join tree allows both inputs to a join to be intermediate results. This explodes the search space, but it can expose more parallelism, since independent subtrees can be computed concurrently. Occasionally it finds cheaper plans, like joining two medium tables before touching a huge one. 

### Physical Plan Cost Model

The components of the cost model include:
- Physical costs, like I/O, CPU cycles, cache misses, RAM usage, and network usage
- Logical costs, like operator output sizes based on table sizes, column cardinality, and index selectivity
- Algorithmic costs, which come from the operator implementation

To calculate the cost of the plan:
1. We first use stats to estimate the input size to each operator
2. Then we estimate the cost of each operator given its input size
3. Then we sum the costs of all the operators in the plan

The DBMS stores internal statistics about tables, attributes, and indexes in its internal catalog. This data may be used for optimizing logical or physical plans.

There are three common ways to store statistics:
- Histograms maintain an occurrence count per value in a column
- Sketches are probabilistic data structures that approximate a count for a given value
- Sampling involves maintaining a subset of each table that is used to compute selectivity

One problem is correlated attributes; each attribute is not independent and uniform. One solution to this is to have multi-dimensional histograms.

## Concurrency Control

A concurrency control protocol is the method used to ensure "correct" results for concurrent operations on a shared object.

For example, we may want to allow multiple threads to read and update a B+ tree at the same time. We need to protect against two types of problems:
- Threads read and modify the contents of a single node at the same time
- Threads traverse and split or merge the tree structure at the same time

The solution to this is ==latch crabbing==, also called latch coupling or hand-over-hand latching. A ==latch== is a concurrency primitive which protects data structures in memory. Similar to a rwlock, a latch in read mode allows multiple threads to read from the same object at the same time, while a latch in write mode only allows one thread to access the object. 

To access or modify a B+ tree, a process needs to:
1. Get latch for parent
2. Get latch for child
3. Release latch for parent and all ancestors if the child is "safe." A safe node is a node that will not split or merge when updated, so it is not full (on insertion) or more than half-full (on deletion).

However, if there are many threads that want to update the B+ tree, taking a write latch on the root every time can become a bottleneck. One solution to this is to use an ==optimistic latching algorithm==. Instead of assuming that there will be a split or merge, we optimistically traverse the three using read latches, and then set a write latch on the leaf. If the leaf is not safe, then we need to release all the latches and restart the traversal with the pessimistic algorithm.

It is also possible to use latch crabbing when we do a scan through the leaf nodes. There will be no deadlocks because all threads will go in the same direction. 

## Transactions

A transaction is the atomic execution of a sequence of multiple executions on a database. It must be ACID, or:
1. Atomic: all actions happen or none happen
2. Consistent: if the DB is consistent before the transaction, it must be consistent after the transaction
3. Isolated: execution of one transaction is isolated from that of other transactions
4. Durable: if a transaction is committed, it is persistent

In SQL, a transaction starts with the `BEGIN` command and stops either with `COMMIT` or `ABORT`. If `ABORT`, all changes are undone so it is like the transaction was never executed at all. If `COMMIT`, the DBMS either saves all of the transaction's changes or aborts it. 

### Conflict Serializability

Even though we want the end result to be as if there is isolation between transactions, we also want to interleave transactions to increase concurrency. Formally, a **serial schedule** is some schedule that does not interleave the actions of different transactions. (There can be multiple serial schedules for multiple concurrent transactions.) An **equivalent schedule** is one where the effect of executing the schedule is identical to the effect of executing another schedule. A **serializable schedule** is a schedule that is equivalent to some serial schedule, such that the resulting state is equivalent to any one of the possible serial executions.

To determine serializability, we check if there are conflicting operations. Two operations conflict if they are by different transactions, they are on the same object, and one of them is a write. If that happens, we can have the following conflicts:
- **Read-write** conflicts result in **unrepeatable reads** (transaction gets different values when reading the same object multiple times)
- **Write-read** conflicts result in **dirty reads**, where one transaction reads data written by another transaction that has not been committed yet
- **Write-write** conflicts leads to **lost updates** where one transaction overwrites uncommitted data from another uncommitted transaction

Two schedules are **conflict equivalent** if they involves the same actions of the same transactions, and every pair of conflicting actions is ordered the same way. A schedule is **conflict serializable** if it is conflict equivalent to some serial schedule. 

We can construct a dependency (precedence) graph where each node represents a transaction. There is an edge from $T_i$ to $T_j$ if an operation $O_i$ conflicts with an operation $O_j$, and $O_i$ appears earlier than $O_j$ in the schedule. A schedule is conflict serializable iff its dependency graph is acyclic.

### Two-Phase Locking

In practice, we need a way to guarantee that all schedules are serializable without knowing the entire schedule ahead of time. The solution to this is to not allow interleavings that yield non-serializable schedules by using ==locks== to protect resources. 

Transactions request locks, the ==lock manager== grants or blocks requests, and then transactions release locks. The lock manager updates its internal lock table to keep track of what transactions hold what locks and what transactions are waiting to acquire any locks.

==Two-phase locking== (2PL) is a concurrency control protocol that determines whether a transaction can access an object **without** needing to know all the queries that a transaction will execute ahead of time. 

1. In the growing phase, each transaction requests the locks it needs from the lock manager.

2. In the shrinking phase, the transaction is only allowed to release or downgrade locks it has acquired. It cannot acquire new locks or upgrade locks. The shrinking phase is denoted by the first release or downgrade.

2PL guarantees conflict-serializability. This is because at the end of the growth phase (==lock point==), the transaction has acquired all the locks it will acquire, and any conflicting transaction must have released the relevant earlier or must wait. The order of lock points gives us the equivalent serial order. 

There are potential schedules that are serializable but would not be allowed by 2PL because locking limits concurrency. 

Furthermore, 2PL can still lead to dirty reads which may require cascading aborts. Suppose transaction $T_1$ acquires the lock, writes, and then releases the lock to $T_2$. Then $T_2$ would be performing a dirty read on the uncommitted data. If we need to abort $T_1$, then we also need to abort $T_2$.  

This can be fixed by ==strong strict two-phase locking==. The transaction is only allowed to release locks after it has been committed or aborted. This allows only conflict serializable schedules, but it is often stronger than needed.

2PL can also result in deadlocks, where there are transactions waiting for locks to be released by each other. There are two ways to deal with deadlocks:

1. The DBMS can detect deadlocks by creating a **waits-for** graph to keep track of what locks each transaction is waiting to acquire. In this graph, transactions are nodes, and there is an edge from $T_i$ to $T_j$ if $T_i$ is waiting for $T_j$ to release a lock. 

    When the DBMS detects a deadlock, it should select a transaction to abort to break the cycle.
    It can select the transaction depending on age, progress, number of items already locked, and number of transactions it has to rollback with it. It should also consider the number of times it was rolled back in order to prevent starvation.

2. The DBMS can also instead prevent deadlocks directly. When a transaction tries to acquire a lock that is held by another transaction, the DBMS can just terminate one of them. 

    There are two common approaches to determining which transaction to terminate. First, transactions have a higher priority if they have an older timestamp. We have a requesting transaction $T_r$ and a holding transaction $T_h$.

    In ==wait-die== (old-waits-for-young), if $T_r$ has a higher priority than $T_h$, then $T_r$ waits for $T_h$. If $T_r$ has a younger timestamp, then it aborts.

    In ==wound-wait== (young-waits-for-old), if $T_r$ has a higher priority than $T_h$, then $T_h$ is aborted and releases the lock. If $T_r$ has a younger timestamp, then it waits.

    When a transaction restarts, its priority is set to its original timestamp to prevent it from getting starved for resources.
