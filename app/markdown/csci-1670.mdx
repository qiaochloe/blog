## Booting

### Stages of Booting

Booting proceeds in stages:
- Stage 0: CPU starts executing the ROM
- Stage 1: ROM loads the bootloader from persistent storage
- Stage 2: Bootloader loads the kernel ("image") into a fixed physical address

In stage 0, there is a fixed circuit that tells the CPU to jump to the first instruction of read-only memory (ROM). ROM can be both directly executed and mapped into RAM. 

The stage 1 bootloader in ROM enables necessary devices (harddisk, SSD, RAM) and loads the stage 2 bootloader from persistent storage into RAM. This bootloader is generally fixed-size and OS-independent.

The stage 2 bootloader is usually a program that is stored in a fixed location on the storage device. (This helps the stage 1 bootloader find it.) The stage 2 bootloader is usually configurable by the programmer. It is generally written in assembly because C assumes that there is a stack, which does not exist yet. 

The stage 2 bootloader is responsible for loading the kernel into a fixed address in RAM. It then jumps to the first instruction of the kernel code. The OS kernel sets up its own stack and memory segments.

x86-64 
- BIOS stands for the Basic I/O System. It intializes hardware (RAM, hard disks, SSD, I/O devices). BIOS is configurable despite living on ROM because it is connected to a CMOS unit (flash) that has a small battery keeping it awake. Note that BIOS is a legacy boot method, and there is a new UEFI method.
- MBR stands for Master Boot Record, and it lives on the very first sector of the hard disk (block 0). When BIOS boots a hard disk, there is a bootloader on the MBR which just finds the next bootloader.
- Examples of "stage 2" bootloaders include GRUB (Linux), Windows Boot Manager, and U-Boot.

Apple Silicon
- For Apple, security is extremely important. Each stage of this boot process is cryptographically verified.
- NOR flash is a type of memory that allows a processor to read and execute code directly from the chip.
- iBoot1 initializes basic hardware.
- iBoot2 builds the Apple Device Tree (ADT) and passes it off to the kernel.
- To run Linux on Apple Silicon (Asahi Linux), it is possible to put m1n1 in Stage 3, which can then run U-Boot, GRUB, and then the Linux kernel.

Raspberry Pi
- Despite the fact that the bootup code lives in the SD card, a big chunk of it is run on the videocore GPU
- Many computers rely on binary blobs of firmware because a lot of device manufacturers do not want to share proprietary pieces of information

## I/O Devices

### Device Drivers

An I/O device will expose some kind of interface that allows us to control the device. These interfaces are commonly called ==device registers==. If we change the bits in a device register, this will physically pull the pin HIGH or LOW and change the state of the device. For example, if you want to send a character to the console, you can write the character to the device's data register. 

==Device drivers== are pieces of software that understands how to interact with the device and its device registers. Device drivers typically run inside of the kernel because interacting with devices is a privileged operation.

<Extra title="Device Example: UART">

UART stands for Universal Asynchronous Receiver-Transmitter. It is a hardware device that can communicate with other devices via a receiver and transmitter.

Note that UART needs to be modified so that it works with the attached device. It can be customized in terms of:
- Baud rate (bits/second)
- Number of bits per character (7 or 8)
- Parity

The UART exposes the following device registers:
- Control Register (CR): turns device and transmission on and off
- Line Control Register (LCRH): configures transmission parameters lke bits per character and parity
- Baud Rate Registers (IBRD, FBRD): set baud rate
- Flag Register (FR): can be read to understand state of hardware (e.g. whether FIFOs are full)
- Data Register (DR): used to actually send and receive data

![UART diagram](/csci-1670/uart-diagram.png)

</Extra>

<Extra title="Device Example: USB">

Similar to UART, USB (Universal Serial Bus) is another protocol that supports peripheral devices. This is possibly what your keyboard or mouse is using when it is plugged into your computer. 

Compared to UART, USB is much more complex, and the USB host controller driver is an enormous amount of code.  

</Extra>

### PMIO and MMIO

**Question**: Now that the devices expose device drivers, how can the CPU actually modify these device drivers?

There are two primary means of communication:
1. In [port-mapped I/O](https://en.wikipedia.org/wiki/Memory-mapped_I/O_and_port-mapped_I/O) (PMIO), there are explicit I/O instructions, such as `in <register>, <port>` and `out <register>, <port>` 
2. In [memory-mapped I/O](https://en.wikipedia.org/wiki/Memory-mapped_I/O_and_port-mapped_I/O) (MMIO), the hardware makes device registers available as if they were memory locations. When the OS issues a read or write to the address, the hardware routes it to the device.

With memory-mapped I/O, the physical address space now contains more than just RAM. On bare metal, the physical address space comprises of:
1. RAM regions used by running programs
2. Reserved regions wired directly to hardware devices (like console)

Note that this device MMIO region is fixed by the hardware, not by the operating system.

![Physical address space](/csci-1670/physical-address-space.png)

When the CPU attempts to access a memory address, there is a selector that either routes it to the connected device or to RAM.

![Physical routing](/csci-1670/physical-routing.png)

## Program Loaders

Programs are stored in an executable format on persistent storage. This executable format may contain:
- Machine code
- Global variables
- Entry point
- Relocation information

Different operating systems have different executable formats:
- Unix/Linux: ELF
- MacOS: Mach-O
- Windows: PE (Portable Executable)

To run a process, the OS needs to read the execuable from disk and run the ==program loader==. The program loader's job is to parse the executable format and load the relevant segments into the memory region chosen for the sepcific process.

The loader must also ensure that all pointers contained in the executable point to the right places in memory. This may involve *relocating* sybols (functions and variables) whose memory addresses aren't known at compile time, but only at load time.

In early operating systems, this loading process was done eagerly, all at once before running the program. Modern operating systems perform this process lazily, loading pieces of code or data only as they are needed during program execution.

For more information about the ELF format, see [CSCI 1655 notes](/csci-1650#elf).

## Processes

### Multiprogramming

Instead of running each process one by one (batch programming), we may want to run more than 1 program on the computer concurrently (multiprogramming).

**Question**: Why do we want multiprogramming?

Compared to the CPU, hardware devices are very slow. If we didn't have concurrency, the CPU might be idle for long periods of time while the program is waiting for I/O. Running several processes concurrently lets the OS multiplex a fast CPU across slow devices.

**Question**: What do we need for multiprogramming?

First, we need to be able to load multiple processes into memory. We also need a way to keep track of each of these processes through some kind of data structures. Finally, we also need a way to switch the CPU between different processes.

### The Process Table

A ==process descriptor==, also known as a process control block (PCB), is a data structure that stores information about a single process. It contains:
- The state of the process (`UNUSED`, `USED`, `RUNNABLE`, `RUNNING`)
- The process ID (PID), so that programs can refer to a process without having a pointer into kernel memory 
- A pointer to the process's stack
- A pointer to its context

A process table is just an array of process descriptors. The kernel maintains a pointer to the descriptor of the current process running on the CPU.

The idle process is always runnable and yields immediately. It is necessary to run the idle process when there is nothing else to schedule.

### Context-Switching

From the CPU's point of view, a running process is just defined by:
1. The general-purpose registers (`x0`-`x30`) which hold the program's live values, base pointer (in `x29`), and return address (in `x30`)
2. The stack pointer (`sp`) which points to the top of the stack
3. The program counter (`pc`) or instruction pointer which contains the address of the next instruction to run
4. The processor state, which includes condition flags (N/Z/C/V) that a following conditional branch depends on, the current exception level, which stack pointer is in use, and which interrupts are masked

To change the process that the CPU is working on, we must save the running process's context and load another process's context. This is called a ==context switch==. 

The mechanism for a context switch usually involves a function to `save_context` and `restore_context`. These functions are usually written in assembly because we need to directly modify registers.

There are two obvious places where we can store the context:
1. Inside the process descriptor. This means that the stack pointer needs to be saved and restored explicitly. It does not generalize well to interrupts. 
2. On the process's own stack. Just before saving, subtract the size of a context from the stack pointer to make room, and then write the registers into that space. The process descriptor stores only a pointer to it.

### Concurrency

In order to do a context switch, the OS needs the ability to stop the CPU from running some process. However, the OS is *itself* a process that needs to run on the CPU. 

There are two ways the OS can get the CPU back from a running process. In ==cooperative concurrency==, the process gives it up voluntarily by calling into the kernel directly (via `yield()`). `yield()` should mimic the behavior of the hardware during an interrupt. 

The problem with cooperative concurrency is that it depends on the process being polite. To get the kernel to forcibly take back the CPU, we need ==preemptive concurrency==. The kernel takes the CPU back by arranging a hardware timer to interrupt the CPU periodically. When the timer fires, the CPU stops executing and jumps into the kernel, where it can schedule another process. 

There are several components that are necessary for preemptive concurrency:
1. A timer device needs to periodically create interrupts
2. An interrupt controller needs to deliver the interrupt to the CPU
3. Once the CPU is interrupted, it should be configured by the hardware manufacturer to jump straight to the trap table
4. The trap table needs to be configured to jump to the asynchronous interrupt handler
5. The asynchronous interrupt handler needs to detect which interrupt occurred and call the appropriate handler (in this case, the timer interrupt handler)

### Scheduling

The kernel needs to figure out which task to run next. The scheduler should be:
1. Fair - no task should starve
2. Fast - picking a task should be cheap
3. Responsive - interactive tasks need low latency
4. Scalable - work on hundreds of CPUs

<Extra title="History of Linux Scheduler">
**The original scheduler (1991-2001)**

The original scheduler was O(n). To pick the next task, it scanned every runnable task and picked the one with the highest "goodness" score. This made it *slow*.

**The O(1) scheduler (2003)**

The O(1) scheduler kept two arrays for each CPU (`active` and `expired`). Each array element was a double-linked list of all runnable tasks at that priority. There was also a bitmap recording which buckets were non-empty. To pick the next task, the scheduler finds the highest priority non-empty list and takes the first element from that list. When a task finished its timeslice, it moved from `active` to `expired`. When `active` emptied, swap the pointers.

**The Completely Fair Scheduler (2007)**

CFS added the idea of ==virtual runtimes==. Each task has a `vruntime`, which is the amount of CPU time it has consumed, weighted by its priority. The scheduler always runs the task with the smallest `vruntime`. This is provably fair because over time, all tasks at the same priority converge on equal CPU share. 

While CFS is fair, predictable, and good for most workloads, it was not great for real-time and latency-sensitive workloads (network I/O, audio,and gaming). A task that wakes up and needs to run quickly might have to wait behind tasks that technically have smaller vruntimes, even if those tasks have been running for a while.

**Earliest Eligible Virtual Deadline First (2023)**

EEVDF added the idea of ==virtual deadlines==. It schedules the task with the most urgent deadline, among those who are eligible to run. A task is eligible if its `vruntime` is at or behind the current virtual time of the queue. 

Each task has:
- `vruntime` - virtual time consumed
- `deadline` - virtual time by which it must run
- `slice` - requested time slice
- `vlag` how far behind or ahead the task is relative to ideal fair share

In most cases, the deadline is computed from the priority, but an application can also explicitly set it.

**References**: [Linux Scheduler Evolution](https://kernel-internals.org/sched/scheduler-evolution/)

</Extra>

## Display

Preemption also allows the OS to respond to devices quickly. When a network packet arrives or when there is a disk read, the data is stored in a limited memory region.The OS needs to respond before that memory region is overwritten by other data. 

To achive this, peripheral devices make an interrupt request. This triggers the interrupt handler, which quickly takes the bytes out of the hardware FIO and puts them into a buffer in memory. Then it terminates and gives control back to the running process. Later, a process consumes the bytes in the buffer.

While processes are waiting for a device, they are in a `BLOCKED` state. Usually, there is a ==wait channel== that allows the blocked process to be associated with some event, such as the address to some kernel data struction. The interrupt handler will wake up every process blocked on the same address by marking them as `RUNNABLE` for the scheduler.

A ==framebuffer== is a region of memory that the hardware continuously reads and then renders on the display. While the screen can be shared across multiple processes, the input keyboard has to go to *some* process. Most windowing systems handle this by setting a *foreground* process or window.

### ARM64 Architecture

ARM64 (also sometimes called "AArch64") is a computer architecture. Practically all mobile device and some laptops (such as Apple Silicon Macbooks) use ARM64 over x86-64 because its processors have significantly lower power consumption. 

Compared to x86, ARM64 has many more registers used for specific tasks.

| Feature                             | x86-64                                                                  | ARM64                                                                                                                        |
| --- | --- | --- |
| General-purpose registers | `%rax`, `%rbx`, `%rcx`, `%rdx`, `%rsi`, `%rdi`, `%rbp`, `%rsp`, `%r8` to `%r15` (16 total) | `x0` to `x30`. `w0` to `w30` are their lower 32-bit halves (writing a `w` register zeroes the upper 32 bits) |
| Stack register | `%rsp` is one of the 16 general-purpose registers | `sp` is a dedicated system register                                                                                          |
| Return address          | The `call` instruction pushes the return address onto the stack.          | The `bl` ("branch with link") instruction puts the return address into `lr`, and `ret` jumps to whatever is in `lr`. |
| Arguments and return values         | Arguments are stored on the stack and return values are stored in `%rax`. | The first eight arguments go into `x0` to `x7`. The return value comes back in `x0` |

Additionally, ARM64 instructions are more specific than those in x86-65:
- ARM64 has special system registers which control the CPU. Only special `mrs` (read) and `msr` (write) instructions can read and write to system registers.
- x86-64 uses `mov` instructions to move data to and from registers. ARM64 requires you to use explicit `lrd` (load) and `str` (store) instructions to load and store from memory.
- x86-64 instructions can vary in length, while each ARM64 instruction is exactly 4 bytes.

### ARM64 Exception Levels

ARM64 has several exception levels which control hardware access permissions.
- EL3 ("secure monitor")
- EL2 ("hypervisor")
- EL1 ("kernel")
- EL0 ("userspace")

The only way to move from a lower EL to a higher EL is to trigger a hardware exception, such as via supervisor calls (`SVC`), hypervisor calls (`HVC`), or secure monitor calls (`SMC`).

The only way to move from a higher EL to a lower EL is by running the instruction `eret` (exception return). `eret` is necessary for context-switching between the process and the kernel.

In an `eret` instruction, the following things happen atomically:
- The processor state is resotred from `SPSR_ELX`
- The program counter is set from register `ELR_ELX`
- The stack pointer is set to the value in `SP_ELX`

`eret` needs to run atomically. If we set the `pc` first, then the CPU will immediately start executing the process's code, and we'll never set `PSTATE`. If we set `PSTATE` first, then kernel code will execute with the process's `PSTATE` (with less privilege or with interrupts enabled).

### ARM64 System Registers

In ARM64, many system registers have distinct instances per exception level. `ELX` is a placeholder for `EL1`, `EL2`, and `EL3`.

| Register    | Name                              | Description                                                                                                                                                    |
|-------------|-----------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `SPSR_ELX`  | ==Saved program status register== | Used to hold the state of the process (`PSTATE`). Its low four bits select teh exception level and the stack pointer to return to.                             |
| `ELR_ELX`   | ==Exception link register==       | Contains the address to resume execution at. It is set by the hardware on an exception and set by the kernel when doing a context switch.                      |
| `ESR_ELX`   | Exception syndrome register       | Contains why the exception happened                                                                                                                            |
| `FAR_ELX`   | Fault address register            | Contains The address that caused the memory fault                                                                                                              |
| `VBAR_EL1`  | Vector base address register      | Contains the address of the exception vector table                                                                                                             |
| `SCTLR_EL1` | System control register           | Contains information about MMU, caches, endianness, and alignment                                                                                              |
| `DAIF`      | Debug, Abort, IRQ, FIQ            | The interrupt-mask bits in `PSTATE`. Note that the bit positions in the `DAIF` register view, in the `DAIFSET` selection, and in `SPSR_ELX` are all different. |

### Raspberry Pi Display Hardware

The Raspberry Pi is really a Broadcom VideoCore graphics processor that happens to have 4 ARM cores attached to it. This means that the display hardware belongs to the GPU, not to the CPU.

The CPU can request access to the display by sending a message through the **mailbox**. The CPU writes the address of a request buffer into one register; the GPU reads it, acts on it, writes results back into the buffer, and posts a reply.
